# Tasks: Agent Access through an MCP Server

**Input**: Design documents from `/specs/007-agent-mcp-server/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md) (R1–R20),
[data-model.md](data-model.md), [contracts/](contracts/) (mcp-tools, management-api, oauth,
ui-screens S1–S6, guidance), [quickstart.md](quickstart.md) (V1–V13)

**Tests**: Included. The plan names them (research R19): pytest for the OAuth flows, the
principal's level table, the user page, search, approvals, the limit and the branch ids; Vitest
(the gate) in `rules/` (`edits.ts` with the reducer's cases replayed, SC-003), `frontend/` (the
reducer, the link builder) and `mcp/` (links, resolution, applicants, findings, the guidance gate
SC-009, the server against a fake backend). Within a story, write the test with the module it pins.

**Organization**: Phase 1 confirms the constitution (1.2.0, amended on 2026-11-05 as the plan's
Complexity Tracking states) and the baselines. Phase 2 moves
the shared TypeScript into the workspace packages **without changing behaviour**, with every gate
green before feature work. Phase 3 lays the backend foundation (settings, tables, the bearer
principal, variant identifiers), the API mirrors and the MCP server's skeleton, which every story
needs. Phases 4–10 are the seven user stories in priority order; within each, the plan's layer
order holds: backend → `rules/` and `api-types/` → `mcp/` → `frontend/`. Phase 11 polishes and
applies the documentation checklist last.

**Size**: 91 tasks, sized from the artifacts: 7 stories, 42 requirements, 24 tools, 5 tables, 3
pages, a workspace of 4 packages and a second service. Phase 3 is large because the OAuth
server, the principal and the MCP skeleton block all seven stories.

## Format: `[ID] [P?] [Story] [Level] Description`

- **[P]**: Can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: Which user story this task belongs to (US1–US7)
- **[Level]**: Who implements the task, judged for Claude Opus 5.5 at that effort (the agents in `.claude/agents/`):
  - **[medium]**: `speckit-task-medium`; mechanical or fully specified work: moves, renames, config, mirrors of existing types, glue code, documentation, tests of behaviour that already exists
  - **[high]**: `speckit-task-high`; new logic that needs design within the task: algorithms, state machines, retry loops, parsers, workers, pages with several states
  - **[xhigh]**: `speckit-task-xhigh`; a mistake is costly and tests written alongside the code are unlikely to catch it: authentication, authorization, tokens and secrets, concurrency and row locks, transactions around external calls, refactors across many files that must not change behaviour, rules that other specs depend on
  - **[lead]**: the coordinator of `/speckit-implement` itself: checkpoints, and tasks that settle an open decision in the spec documents that later tasks depend on

## Path Conventions

Web application in an npm workspace (research R1). **Paths below are the ones after Phase 2**:
`api-types/src/` (the API mirrors, was `frontend/src/types/`), `rules/src/` (the pure rules
logic, was `frontend/src/utils/rules/`), `frontend/src/` (the SPA; `src/workers/` holds the two
browser Worker entries), `mcp/src/` (the MCP server), `backend/app/` (FastAPI). Commands: the
Node gates run from the repository root (`npm run lint && npm test && npm run build`), the
backend's in `backend/`. Line numbers are from the checkout of 2026-11-05 and only help to find
the place.

## Phase 4: User Story 1 - Connect an agent and let it read the connections (Priority: P1) 🎯 MVP

**Goal**: A team member connects an MCP client through the browser sign-in (or a personal access
token), chooses an access level, and the agent searches and reads connections and the catalog in
layers. The user page lists, changes and revokes agent connections and tokens.

**Independent Test**: Connect an MCP client with "Read only". Check that the agent finds a
connection among many by part of its name, reads its documents and one variant's rules, and is
refused when it tries to change a draft. Check that the user page lists the client with read-only
access. Raise it to "Read and edit drafts" and check that the agent can now change a draft without
connecting again; lower it to "Read only" and check that the next change is refused. Revoke it,
and check that the agent's next call is refused. (quickstart V1–V4)

## Notes

- [P] tasks touch different files and depend on nothing unfinished.
- The [Story] label maps a task to the user story it serves (spec.md).
- Every backend task passes Ruff, mypy (`app/ scripts/ tests/`) and pytest before it is done;
  every task in a Node package passes `npm run lint && npm test && npm run build` **from the root**,
  since a change in `rules/` or `api-types/` must compile in both consumers.
- Boundaries hold from the move on: `rules/` imports `api-types` and itself; `frontend/` and
  `mcp/` never import each other; the root ESLint config enforces it.
- Nothing about tokens, codes, applicants, findings or results is stored or logged: no
  `console.*` in `mcp/src/` except `log.ts`, nothing in `rules/`.
- The migration is read and corrected by hand (constitution V); no committed migration is edited.
- Specs state final decisions: a research point settled while coding (R20) is rewritten in place,
  not annotated.
- Commit after each task or logical group; stop at any checkpoint to validate the story.
