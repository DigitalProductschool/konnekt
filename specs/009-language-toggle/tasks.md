## Format: `[ID] [P?] [Story] [Level] Description`

- **[P]**: can run in parallel: different folders, no dependency on an unfinished task. The waves
  and batches of a phase are in its "Delegation" section; nothing else lists them.
- **[Story]**: the user story a task delivers: US1 (the switch and the German UI), US2 (the choice
  is remembered), US3 (the server's and the rules' copy). The foundations' provider and resolver
  are US2's whole implementation and carry its label; setup, checkpoint and documentation tasks
  carry none.
- **[Level]**: who takes the task in `/speckit-implement`, judged for Claude Opus 5.5 at that
  effort.
  - **[medium]**: `speckit-task-medium`: mechanical or fully specified work: moves, renames,
    config, mirrors of existing types, glue code, documentation, tests of behaviour that already
    exists, German written from the glossary into a table whose shape is given.
  - **[high]**: `speckit-task-high`: new logic that needs design within the task: algorithms,
    state machines, retry loops, parsers, workers, pages with several states, German sentence
    templates with their own grammar, the per-node loop against Figma, a screen's German check.
  - **[xhigh]**: `speckit-task-xhigh`: a mistake is costly and tests written alongside the code
    are unlikely to catch it: authentication, authorization, tokens and secrets, concurrency and
    row locks, transactions around external calls, refactors across many files that must not
    change behaviour, rules that other specs depend on.
  - **[lead]**: the coordinator does it itself: the checkpoints, and tasks that settle an open
    decision in the spec documents that later tasks depend on.
- **Every task line carries**: what it builds, the requirements it meets (FR-#, SC-#), the research
  decision it applies (R#), the glossary section it uses (G§#) where it writes German, the files it
  edits, and the gates it ends with. Phase 5's tasks also name the screen (S#) and the spec 008
  table they check against; phase 2's names the Figma node.

## Rules every task follows (plan.md, "Rules for `/speckit-tasks`")

- **German is written in the task that makes the table**, from the glossary (G§1 style, G§2
  product terms, G§3 the rules' vocabulary and sentences, G§4 the catalog and option sets); a
  missing term is added to the glossary in the same task, never translated ad hoc. Formal "Sie",
  neutral forms, German quotes „…“, nouns capitalised, the infinitive on buttons (G§1). Every
  German string differs from its English one unless the word is in `copy.test.ts`'s allowlist.
- **English stays word for word** (FR-014): moving a string into a table changes no English text;
  the existing English assertions in tests are not edited, only given `'en'` or the default. A
  task that would have to change an English string stops and reports it.
- **Behaviour stays the baseline's** (FR-016): a reducer, hook or helper keeps its tests passing;
  a code replaces a string comparison without changing the branch taken (R10); no component is
  re-keyed on the language.
- **Nothing logged, stored or sent** about the language (FR-018): no `console.*` in the provider,
  the hooks, `rules/src/`, `utils/language/`; the backend never logs the header or a `Text`;
  findings, personas and local drafts stay unlogged and unsent (specs 003–005).
- **What leaves the website stays English** (FR-017): `/api/connect/`, EUDIPLO, the MCP server's
  answers (no `language` is ever passed from `mcp/src/`), stored data ("Standard", "Rule NN",
  saved messages). `ApiResponse.message` and the OAuth RFC bodies stay English.
- **Content is never in a table** (FR-007): names, descriptions, variant names, saved citizen
  messages, usernames, agents' requests, identifiers, "Konnekt", "Standard".
- **Gates**: a task in a Node package ends with `npm run lint && npm test && npm run build` from
  the root; a backend task with `uv run ruff check --fix . && uv run ruff format . && uv run mypy
  app/ scripts/ tests/` and `DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5435/template_db_test
  uv run pytest` in `backend/`; a task that touches the fixture script runs
  `uv run python -m scripts.export_check_fixtures --check`. A task that edits only
  `specs/` runs no gate.
- **Reports**: a task's report lists the files it changed, the glossary terms it added, every
  UNCERTAIN decision, and (phases 2, 5, 6) the rows it appended to design-notes §2. The
  coordinator ticks a task only when its gates are green and its rows are clean.

## Phase 2: User Story 1 — The switch in the header (Priority: P1) 🎯 MVP, part 1

**Goal**: the design's "DE | EN" pill in the header of every screen, operable by keyboard,
announced by the languages' own names, switching the language without a reload (FR-001, FR-003,
FR-010, FR-011, FR-015). With phase 1 this is the switch of US1; the German copy behind it comes in
phases 3–5.

**Independent Test**: on `/login`, `/`, `/form-connections/:id` and a scrolled page, at 1440 px and
320 px / 200 %, the pill sits in the header's right group as the node draws it, Tab reaches both

## Implementation Strategy

### MVP First (User Story 1: the switch, then its copy)

1. Phase 1 Foundations (T001–T010): the language on both sides, the provider, the header.
2. Phase 2 The switch (T011–T013): the pill on every screen, the per-node loop.
3. **STOP and VALIDATE**: the switch changes `<html lang>` and the kit's texts on every screen without a reload (quickstart V1 step 1 without the copy; V9's keyboard part). This proves the provider, the header and the switch; it is **not** shippable: a switch that leaves the copy English has no value (spec, US1 "Why this priority").
4. Phases 3 and 4 (T014–T029): the server and the rules package speak German.
5. Phase 5 (T030–T043): the screens' copy. **STOP and VALIDATE**: US1's five acceptance scenarios on the screens (T043).

### Incremental Delivery (one chat per phase, research R12)

1. Foundations → the gates green, US2 done in substance.
2. The switch → V1 step 1, the §2.1 table.
3. The backend's texts → V3 steps 3 and 4 with `curl`.
4. The rules package → the tests' German cases, the parity fixture matched, the MCP untouched.
5. The frontend's copy (four chats: hooks and shared components; S1–S5 and S8; the editor shell, S9/S11/S12 and the details; S10, S13, S19–S21) → US1's scenarios.
6. The German walk → V1–V11, the review log.
7. Documentation and close → `/speckit-converge`, the checklist, the report; the user commits on the other machine.

### Parallel Team Strategy

The phases are sequential by design (one provider, one glossary, one `design-notes.md`), so the
parallelism is inside a phase: up to three Opus task agents on different folders. A second person
can run Phase 3 (the backend) while the first starts Phase 4's T022; in Phase 5, a second person can
take the hooks (T030) while the first turns the shared components (T031, T032), and the screen
batches can be split between them three at a time.
