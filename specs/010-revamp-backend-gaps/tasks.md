## Format: `[ID] [P?] [Story] [Level] Description`

- **[P]**: can run in parallel: different folders, no dependency on an unfinished task. The waves
  and batches of a phase are in its "Delegation" section; nothing else lists them.
- **[Story]**: the user story a task delivers (US1–US9 of spec.md). Every task of a story's phase
  carries it, its walk and its checkpoint included; setup, foundations and close carry none.
- **[Level]**: who takes the task in `/speckit-implement`, judged for Claude Opus 5.5 at that
  effort.
  - **[medium]**: `speckit-task-medium`: mechanical or fully specified work: moves, renames,
    config, mirrors of existing types, glue code, documentation, tests of behaviour that already
    exists, a migration that adds columns, an MCP tool that follows an existing tool, copy tables
    written from `contracts/copy.md`.
  - **[high]**: `speckit-task-high`: new logic that needs design within the task: algorithms,
    state machines, retry loops, parsers, workers, pages with several states, a migration with a
    backfill, the per-node loop against Figma, a scripted walk or sweep.
  - **[xhigh]**: `speckit-task-xhigh`: a mistake is costly and tests written alongside the code
    are unlikely to catch it: authentication, authorization, tokens and secrets, concurrency and
    row locks, transactions around external calls, refactors across many files that must not
    change behaviour, rules that other specs depend on.
  - **[lead]**: the coordinator does it itself: the checkpoints, and tasks that settle an open
    decision in the spec documents that later tasks depend on.
- **Every task line carries**: what it builds; `items:` the requirements (FR-#, SC-#), the
  decision (R#), the contract section (the endpoint or shape, the screen S# or C#, the tool) and,
  for a UI task, the frames (node ids) and the audit's items (F#, W#); `depends on` where the
  order isn't the list's; `files:`; `gates:`; and `size:` the estimate the coordinator plans with:
  nodes read, states built or checked, expected screenshots and tool calls.

## Rules every task follows (plan.md, "Rules for `/speckit-tasks`")

- **Vertical slices, contract parity per task**: a task that changes `schemas.py` changes
  `api-types/src/` and whatever reads the shape in the same task, as its `files:` say. The MCP
  guidance changes in the task that changes the tool (`npm test -w mcp` fails otherwise).
- **The backend's order and locks**: model → schemas → migration → services → router → tests. A
  service that changes a connection takes `actor` and records the change with
  `activity.record()` under the connection's row lock, in the transaction that makes the change.
  No transaction is held while EUDIPLO answers. One migration per slice, generated with
  `--autogenerate`, then read and completed by hand as data-model §9 says; a committed migration is
  never edited.
- **Copy**: the frames' and the spec's English word for word; the undrawn sentences from
  [contracts/copy.md](contracts/copy.md); German in the task that makes the table, from spec 009's
  glossary; typographic apostrophes and quotes as the frames draw them.
- **Behaviour stays the baseline's** outside the nine items: an existing reducer, service or
  helper keeps its tests passing; a test changes only for a requirement of this spec, and the task
  names it. What a frame shows of an out-of-scope item is not built (FR-076): it is a row "not
  built, F#" in the task's table.
- **The per-node loop** (quickstart, `docs/FIGMA-WORKFLOW.md` §3–§4) for every frame a UI task
  names: `get_design_context` and `get_screenshot` on the node, the page in the same state at
  1440 px (a 1455 px window in Chromium), the font check, the numeric check, the screenshot
  comparison. The table's rows are `frame | state | width | element | property | Figma | actual |
  result`; `result` is `match` or the decided item it cites. A task reads at most about eight
  nodes, and at most three tasks with Figma calls run at a time. **A frame that changed since the
  audit is not built**: the task stops on that node and reports it as UNCERTAIN.
- **Every state a UI task builds also gets its measured narrow rows**, in English, read with
  `browser_evaluate` at 320 CSS px and at 160 CSS px (the 320 px window at 200 % zoom, `narrow:`):
  no horizontal scroll (`scrollWidth <= clientWidth` on `html`), nothing clipped or off-screen,
  exactly one `h1`, the focus ring after keyboard focus and none after a click. Phase 12's sweeps
  cite these rows and don't repeat them.
- **Walks and sweeps are script-first.** A task that checks many items across many states (a
  quickstart scenario, routes × states × widths, text pairs, controls × interaction states)
  writes a Playwright script in the scratchpad that reaches each state, measures everything that
  can be measured and writes a CSV with one row per measure plus a summary grouped by state and
  measure: horizontal scroll, clipped or off-screen elements, the `h1` count, focus-visible after
  a click and after the keyboard, contrast (colours converted through a canvas context, alpha and
  `opacity` composited down to the first opaque background), computed durations, label widths, the
  live regions' texts, the texts of FR-076 that must not appear. The agent reads the summary and
  opens a screenshot only for a row that fails or that the script marks `unsure`. `playwright-core`
  is installed into the scratchpad and launches `/usr/bin/chromium` and Playwright's Firefox; no
  `package.json` of the repository changes.
- **A parallel sweep reports and never fixes**: its report lists the defects (state, measure,
  element, value, file it suspects). One later task owns the fixes. A story's walk is the only
  batch of its wave, so it fixes what it finds in its story's files and reruns the failed rows.
- **Shared records have one writer.** Only the coordinator edits `tasks.md`, `design-notes.md`,
  spec 009's glossary and `contracts/copy.md`, unless a task's `files:` name one of them. A task
  writes its verification table to `<scratchpad>/tables/T###.md` and reports the file with its
  count of rows and of open rows; after the wave the coordinator appends the files to design-notes
  §2 with `cat`, without reading them. A glossary term a task had to add, a sentence of
  `contracts/copy.md` it would word differently and every UNCERTAIN decision go into its report;
  the coordinator records them (the glossary, design-notes §4.3).
- **One browser per batch**: where a wave has several batches that drive a browser, its
  Delegation line names each one's: the `playwright-chrome` MCP, the `playwright-firefox` MCP, or
  a scripted `playwright-core` Chromium. Backend batches never run side by side: the tests empty
  one shared database.
- **Nothing new in the logs** beyond ids and counts; no `console.*` in the places CLAUDE.md
  names; the activity, the names and the dates never reach a log line. Generated files
  (`rules/src/fixtures/*.json`, `rules/src/checks/caseFolding.ts`,
  `rules/src/checks/fixtures/evaluator-vectors.json`) are written only by
  `uv run python -m scripts.export_check_fixtures`.
- **Gates**, named in each task: **root** is `npm run lint && npm test && npm run build` from the
  root; **backend** is `uv run ruff check --fix . && uv run ruff format . && uv run mypy app/
  scripts/ tests/` and `DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5435/template_db_test
  uv run pytest` in `backend/`; **fixtures** is `uv run python -m scripts.export_check_fixtures
  --check`. A gate that fails in a file of another batch of the same wave is reported, not fixed;
  the coordinator reruns the gates after the wave.
- **Reports**: the files changed, the gates' results, the table file with its counts, the glossary
  terms and copy changes asked for, and every UNCERTAIN decision. The coordinator ticks a task
  only when its gates are green and its table has no open row.
- **For the coordinator of `/speckit-implement`**:
  - Follow each phase's "Delegation": one agent per batch at the batch's level, the waves in
    order. Read Figma and screenshots only through the task agents.
  - **A note carried from one task to a later one** is appended to that task's line as
    `carried from T###: …`. When a line collects more than three of them, move them into a
    separate "decide" task in the same phase, placed before the task that depends on the answer,
    instead of appending them to a walk or a sweep. An open question, a "check X and decide" note
    and a question for the designer always get such a task.
  - **Before delegating, check the task's `size:`** against what earlier tasks added to it. Split
    any task above about 40 screenshots or 150 tool calls into tasks of the same level that share
    no file, or that run in consecutive waves.
  - A sweep rechecks only the states that the per-task tables of design-notes §2.1 and the walks
    of §2.2 didn't cover; its line names them. When a later task changed a screen after its table
    was written, add that screen's states to the sweep's line before delegating it.
