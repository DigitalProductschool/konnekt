its build and deploy files.

- **Removed (backend)**:
  - the example router `app/routers/team_members.py` and the mock wallet handshake
    `app/routers/id_verification.py`;

  - the team-member, `AskIdResponse` and `PersonIdResponse` schemas;

  - the `api_key` setting, the `api_key` value that `/api/health` exposes, and `API_KEY` in
    `.env.example` and `docker-compose.prod.yml`.
- **Removed (frontend)**:
  - `src/pages/TeamMembers/` and `src/api/team-members.ts`;
  - the team-member and pagination types in `src/types/api.ts`;
  - the tracked build artifact `frontend/tsconfig.app.tsbuildinfo`, with `*.tsbuildinfo` added to
    `.gitignore`.
- **Kept**:
  - `app/__init__.py`, `config.py`, `db.py` and `errors.py`;
  - the generic `ApiResponse` and `ApiErrorResponse` envelopes and the `to_iso_utc` helper;
  - Alembic, both Dockerfiles, both compose files, `nginx.conf` (extended in R13), and the ESLint,
    Prettier, Ruff, mypy and pre-commit configuration;
  - the `ApiError` and `handleResponse` pattern, moved into a shared `src/api/client.ts`.
- **Migration history**: the committed `alembic/versions/v0_add_team_members.py` stays. A new
  autogenerated migration drops `team_members` and creates the new tables.
- **Documentation**:
  - `README.md` contains no example code.
  - The template examples in `CLAUDE.md` are the backend structure listing that shows
    `routers/team_members.py` and the "Full Stack Example". Those in `docs/ARCHITECTURE.md` are
    the error and naming examples. All of them are rewritten to the new structure as part of the
    documentation checklist.
  - The naming-convention tables in `CLAUDE.md` keep their generic `TeamMember` examples, because
    they illustrate conventions rather than describe code.

**Rationale**: "Start from scratch but use the same technology and stack" separates feature code,
which goes, from the stack configuration, which stays. Constitution V forbids editing committed
migrations. The template has probably been deployed, because the mock APIs and `API_KEY` exist in
the production compose file. Deleting `v0` would then break `alembic upgrade head` on that
database: Alembic could not find the revision recorded in `alembic_version`.

**Alternatives considered**:
- Deleting `backend/` and `frontend/` and scaffolding again: this produces the same files, so it
  only adds churn.
- Deleting `v0` and starting a fresh migration history: this violates Constitution V and breaks
  any database that has already applied `v0`.

## R2. EUDIPLO integration model **(user: hosted instance; shared tenant accepted for now)**

**Decision**:
- **Instance**: the middleware uses the team's hosted EUDIPLO (Coolify, tenant `dps`). Automated
  tests replace EUDIPLO with a fake (R17).
- **Calls**: the middleware calls only the EUDIPLO management API (`/api/*`), authenticated with
  the OAuth client-credentials flow.
- **Request configurations**: each saved revision of a form connection becomes one immutable
  EUDIPLO presentation configuration, with the id `fc-<form connection id>-r<revision>`.
- **Requests**: each document request is one `POST /api/verifier/offer` against that
  configuration. Its `reference` is set to the middleware's internal request id, never to personal
  data.
- **Client permissions**: the middleware's EUDIPLO API client needs the roles
  `presentation:request` and `presentation:manage`, and no `allowedPresentationConfigs`
  allow-list. It needs no issuance role.

**Creating a revision safely**:
1. The middleware locks the `form_connections` row (`SELECT … FOR UPDATE`) before it takes the
   next revision number. This way two simultaneous edits can't create the same configuration id.
2. It creates the EUDIPLO configuration.
3. It inserts the revision.

If the database commit fails after step 2, the middleware tries to delete the configuration it
just created and logs the outcome. That way an orphaned configuration is at most logged, and
never silently left behind.

**Keeping configurations in step with settings and the catalog**: each revision stores
`lifetime_seconds` and a `config_hash`. The hash is the SHA-256 of the canonical configuration body
without its `id` and `description`, and the body depends on the catalog, `EUDIPLO_TRUST_LIST_ID`
and `REQUEST_LIFETIME_SECONDS`. Leaving out `description`, which holds the form connection's name,
means a rename never creates a revision.

- **When the check runs**: after every start. The worker rebuilds the configuration body for the
  current revision of every form connection that isn't deleted.
- **When something changed**: if the hash differs, the worker creates a new revision with the same
  documents, so new requests use the new settings at once. Requests already in progress keep their
  revision (FR-005).
- **Example**: switching the trust list from test issuers to production issuers takes effect
  everywhere without anyone editing a form connection.

**Rationale**:
- **Why `presentation:manage`**: `POST /api/verifier/offer` cannot take a DCQL query inline. The
  documents and fields have to live in a presentation configuration, so the middleware must create
  and delete configurations. This is what lets DO.IT configure forms without a developer (FR-003,
  SC-002).
- **Why no allow-list**: a non-empty allow-list would reject every configuration the middleware
  creates later with a `403`. An empty allow-list permits all of them.
- **Why no issuance role**: issuing documents is out of scope.
- **Why immutable revisions**: the wallet fetches the request object after the trigger, and
  EUDIPLO checks the response against the configuration. Editing one shared configuration in place
  could therefore change a request that is already in progress. Immutable revisions keep
  in-progress requests on the configuration they started with (FR-005).
- **Configuration settings**: `lifeTime` comes from `REQUEST_LIFETIME_SECONDS` (600 s, FR-012).
  `statusCheckMode` is set explicitly to `strict` (FR-010). `description` holds the form
  connection's name, which EUDIPLO uses internally only.
- **Self-healing**: if `POST /api/verifier/offer` answers `409`, the configuration is missing. The
  middleware then re-creates it from the stored revision and retries once. This covers
  configurations removed by hand from the shared tenant.

**Accepted risks**:
1. **`presentation:manage` is broader than needed**. Besides presentation configurations, it also
   lets the client manage trust lists, key chains and webhook endpoints in the tenant
   (`docs/EUDIPLO.md` §4, §5). EUDIPLO 9 has no narrower role that can create configurations.
   - Mitigations: the client secret lives only in the backend's environment, and the middleware's
     code calls only the seven endpoints in [contracts/eudiplo-usage.md](contracts/eudiplo-usage.md).
2. **One tenant for every environment (user: accept for now)**. Development machines, PR previews
   and production share tenant `dps` and one API client until real citizens use the service.
   - An API client sees every presentation session of its tenant. Anyone holding the client
     secret, which includes every developer's `.env`, can therefore read and delete the sessions
     of every environment, including the documents shared in production.
   - Before real citizens use the service, production should get its own tenant or instance
     (R19). DO.IT owns this (user).

**Alternatives considered**:
- One mutable configuration per form connection: this breaks FR-005.
- DO.IT creating configurations in the EUDIPLO console: this defeats the feature's purpose.
- The client that `docs/EUDIPLO.md` §4 suggests (`issuance:offer` + `presentation:request`): it
  cannot create configurations.
- `@eudiplo/sdk-core`: it is a JavaScript package, the backend is Python, and the management token
  must never reach the browser (EUDIPLO.md §10).

**Effect on other documents**: `docs/EUDIPLO.md` §4 ("Our middleware's client") and the
"Middleware client" row in §11 both have to be updated to these two roles, with no allow-list.

## R3. From documents and fields to a DCQL query

**Decision**: The middleware builds the DCQL query of a revision deterministically from the
revision's documents and the catalog (R4).

- **One credential query per document**: its `id` is the document type key (`pid`, `mdl`). Each
  document type can appear at most once per form connection.
- **Format per document type**, from the catalog:
  - PID: `format: dc+sd-jwt` with `meta.vct_values: ["urn:eudi:pid:1", "urn:eudi:pid:de:1"]`, which
    accepts the EU base type and the German domestic type;
  - mobile driving licence: `format: mso_mdoc` with `meta.doctype_value: org.iso.18013.5.1.mDL`.
- **Claims**: each selected field becomes `{"path": [...]}`, listed in catalog order. For SD-JWT VC
  the path is the claim path, such as `["address", "locality"]`. For mdoc it is
  `[namespace, element]`.
- **No `credential_sets` and no `claim_sets`**: with neither, every credential query and every
  claim is required. This is exactly the spec's all-or-nothing assumption. There is no per-claim
  "optional" flag in DCQL.
- **Issuer trust**: every credential query carries the same `trusted_authorities`:
  `[{"type": "etsi_tl", "values": [{"trustListId": EUDIPLO_TRUST_LIST_ID}]}]`.
- **Registration certificate**: the configuration has no `registration_cert` (see R19).

**Rationale**:
- **Trust list**: EUDIPLO documents that "a credential query without `trusted_authorities` is
  verified without any issuer check". Leaving it out would therefore violate FR-010 ("comes from a
  trusted issuer").
  - One shared trust list matters because Paradym, the first test wallet, "cannot handle differing
    `trusted_authorities` in DCQL queries".
  - While `EUDIPLO_TRUST_LIST_ID` is empty, the middleware refuses to create a configuration and
    answers `503 Not configured`. FR-010 therefore can't be bypassed without anyone noticing.
    **(user, 2026-10-11)** The answer's message is generic and carries an `error_id`, and only the
    backend's log names the missing setting, under that ID. Naming it in the message, as first
    planned, showed backend configuration in the UI (bug `config-error-leak`).
- **Formats**: the mDL rulebook allows only the ISO 18013-5 encoding for mDLs. The PID is offered
  in both formats. SD-JWT VC is chosen because both test wallets support it, and so do the EU and
  German PID providers.

**How FR-010 is covered**: EUDIPLO checks each document, so the middleware doesn't repeat these
checks (EUDIPLO.md §2).

| FR-010 asks for | How EUDIPLO checks it | Evidence |
|---|---|---|
| Authentic and unaltered | Issuer signature | `signature_invalid` |
| Trusted issuer | Trust list in `trusted_authorities` | `no_trust_chain_to_root`, `trust_chain_not_trusted` |
| Not revoked or suspended | Status lists, with `statusCheckMode: strict` | Status-list and revocation-certificate rules in EUDIPLO's trust-list documentation |
| Presented by its holder | Holder binding: key binding for SD-JWT VC, device authentication for mdoc | EUDIPLO.md §2; `verifyDeviceResponse` in EUDIPLO's mdoc verifier |
| Not expired | Credential time checks | Inferred from the presentation configuration's `skewSeconds` field, which is described as "clock skew tolerance for credential time checks". No dedicated failure code is documented. **Verify at implementation**: present an expired test credential and expect `verification_failed` (quickstart V3) |

**Alternatives considered**:
- Requesting the PID in both formats through `credential_sets` alternatives: this doubles the query
  and result handling for no requirement. It can be added later as a second catalog variant.
- Asking for the PID as mdoc: viable, but nothing calls for it.

## R4. Document type catalog (FR-002)

**Decision**: The catalog is a backend Python module, `app/catalog.py`, versioned with the code
and not stored in the database. The API serves it read-only at `GET /api/document-types`.

- **Contents**: two document types.
  - `pid`: the PID, built from the attributes in PID rulebook v1.7, in its SD-JWT VC encoding.
    This includes the rulebook's extension `address.house_number`, alongside `address.street_address`,
    which the rulebook defines as "the name of the street … including the house number". It also
    includes the mandatory metadata `issuing_authority` and `issuing_country`.
  - `mdl`: the mobile driving licence, built from the ISO/IEC 18013-5 data elements in the
    namespace `org.iso.18013.5.1`.
- **What each field holds**: a stable `key`, a readable `label`, and the claim path. The full lists
  are in [data-model.md](data-model.md#document-type-catalog).
- **Not offered**:
  - mDL elements whose names vary by issuer (`age_over_NN`, `biometric_template_xx`);
  - the rulebook's technical PID attributes (`trust_anchor`, `attestation_legal_category`).
- **Labels**: they are UI copy. Their language and wording follow the Figma design. The plan lists
  English labels as placeholders.
- **Changes**: changing the catalog changes the configurations it generates, so R2's re-sync
  applies changes to existing form connections automatically.

**Rationale**: The catalog describes credential formats. A wrong claim path silently breaks
requests, so changes need review and a deployment, not an admin form. FR-002 asks for "at least"
these two documents, and adding a type means adding one catalog entry.

**Alternatives considered**:
- A database table with an admin UI: no requirement asks for it, and the risk of misconfiguration
  is higher.
- Fetching the fields from issuer metadata at runtime: this needs network access, and issuers
  differ.

## R5. Request statuses (FR-011) and how EUDIPLO maps to them

**Decision**: A document request has one of the statuses `pending`, `completed`, `declined`,
`verification_failed`, `expired` or `unavailable`. These are the machine forms of the spec's
statuses; `verification_failed` stands for "verification failed".

| EUDIPLO session | Request status |
|---|---|
| `active` or `fetched` | `pending` |
| `completed` | `completed` |
| `failed` with a wallet error code: `access_denied`, `invalid_request`, `invalid_client`, `invalid_scope`, `unauthorized_client`, `unsupported_response_type`, `server_error`, `temporarily_unavailable`, `vp_formats_not_supported`, `invalid_request_uri_method`, `invalid_transaction_data`, `wallet_unavailable` | `declined` |
| `failed` with a verification code (`signature_invalid`, `no_trust_chain_to_root`, `trust_chain_not_trusted`, `trust_list_unavailable`, `certificate_expired`, `x5c_missing`, `verification_error`, `claim_value_mismatch`), an unknown code, or no code (for example "Missing required claims") | `verification_failed` |
| Still `active` or `fetched` at the last check after the expiry time (R7), or `expired` | `expired` |
| The form connection was deactivated or deleted while the request was open (R9) | `unavailable` |

- **The last check before expiry** applies this same table. A citizen who declined or failed
  verification just before the deadline therefore gets `declined` or `verification_failed`, not
  `expired`.
- **What is stored**: EUDIPLO's `failureCode` is stored with the request for diagnostics. It is
  not personal data, and it is never sent to serviceBW.
- **Transitions**: `pending` can move to any of the other statuses. An open `completed` request
  can still move to `unavailable` (R9). Nothing else changes once set.
- **A decline only reaches the middleware if the wallet reports it**. When the citizen cancels, an
  OID4VP wallet should send an `access_denied` error response, and that response makes the status
  `declined` within about 2 seconds. A wallet that simply closes without answering leaves the
  request `pending` until it becomes `expired`, 10 minutes after the trigger. **Checked on
  2026-10-13** (bug report `wallet-decline-pending`):
  - **EUDIPLO 9.0.0 records a wallet error response** (source at tag `v9.0.0`). It accepts one as
    form parameters or inside the encrypted `direct_post.jwt` response, and stores it as `failed`
    with the wallet's code as `failureCode` (`oid4vp.service.ts`, `fail-presentation-response.ts`).
    The update moves `updatedAt` forward, so the sync (R6) picks the session up.
  - **The test wallets send none** (source). Paradym 1.20.2 (`0bfd4e1`) and `main` (`226083d`,
    1.21.0) only log a decline in the wallet's own activity list. The EU reference app for Android
    (`main` @ `7f40440`) stops the flow and never calls wallet-core's `rejectRemotePresentation()`.
    The EU reference app for iOS wasn't checked.
  - **Live, with Paradym 1.20.2 (build 94)**: after a decline on the consent screen, EUDIPLO's
    session stayed `fetched` without a `failureCode`, and the request became `expired`. Leaving
    Paradym's "no matching card" screen ends the same way.
  - The middleware's side is covered by `test_a_wallet_error_reaches_the_pull_within_one_sync`.
    Quickstart V3 has a wallet-free check of it on a deployment.
  - Treating a session that stays `fetched` as declined was rejected: a citizen who is still
    choosing or entering a PIN would lose an approval that comes later.

**Rationale**:
- **Wallet errors**: when the wallet answers with an OAuth or OID4VP error, that code becomes
  `failureCode`.
  - `access_denied` covers both a citizen who cancels and a wallet that lacks a document, which
    matches the spec's edge case.
  - The remaining wallet codes are technical errors where likewise nothing was shared. Of the six
    statuses, `declined` is the closest fit.
- **Unknown codes**: they map to `verification_failed`, so that a new verification code from a
  later EUDIPLO version never looks like a citizen's choice.
- **Why explicit statuses matter**: they let serviceBW stop waiting and show an error as soon as
  the citizen declines. The mock middleware this replaces answered "not found" both while waiting
  and after a failure (R20).

**Alternatives considered**:
- Only `access_denied` maps to `declined`, and everything else to `verification_failed`. Technical
  wallet errors would then read as rejected documents.

## R6. How results are detected: polling EUDIPLO

**Decision**: The middleware asks EUDIPLO for results; it does not receive EUDIPLO webhooks.

- **Each cycle**: every 2 seconds, the background worker (R7) calls
  `GET /api/session?type=presentation&updatedFrom=<cursor>`.
  - It uses each item's `id`, `status`, `failureCode`, `consumedAt` and `updatedAt`, and ignores
    sessions it doesn't know.
  - **Verify at implementation**: whether the list items carry `failureCode` and `consumedAt`. If
    they don't, the worker reads each changed session with `GET /api/session/{id}`, and discards its
    `credentials` immediately without storing or logging them (R8). **Checked (T018, R19 item 4)**:
    per the OpenAPI they carry both, when set.
- **Cursor**: the latest `updatedAt` value seen from EUDIPLO, minus a 5-second overlap. It is never
  taken from the middleware's own clock, so a clock difference between the two servers can't hide
  an update. After a restart the cursor begins at the creation time of the oldest open request.
  Processing is idempotent per session, so repeated items do no harm.
- **Verify at implementation**: whether `GET /api/session` pages its results. **Checked (T018, R19
  item 4)**: it does, with at most 100 items per page.

**Rationale**:
- **Reachability**: an EUDIPLO webhook would have to call the middleware.
  - The hosted EUDIPLO can't reach a backend inside the restricted network or on a developer's
    machine.
  - EUDIPLO's outbound-address policy also allows only public HTTPS targets by default.
    `OUTBOUND_URL_ALLOW_*` can relax that, but it is an instance-wide setting of the hosted EUDIPLO.

  Polling needs only outbound calls from the middleware, so it works the same in development and
  production.
- **Speed and load**: one list call per cycle stays cheap however many requests are pending. A
  2-second cycle keeps SC-004 (documents within 5 seconds) with margin.
- **Expiry**: EUDIPLO sends no webhook when a request expires. The middleware must track expiry
  itself anyway (EUDIPLO.md §10), and the same loop does that.
- **Deviation**: `docs/EUDIPLO.md` §13 recommends "webhook + polling fallback". The polling path is
  that fallback, and an EUDIPLO webhook can be added later without changing the data model.

**Alternatives considered**:
- EUDIPLO webhook plus polling: this needs an inbound path from EUDIPLO into the restricted
  network, for at most 2 seconds of latency.
- A per-session SSE stream (`/api/session/{id}/events`): 100 long-lived connections from a sync
  backend.
- Polling `GET /api/session/{id}` for each pending request: up to 50 calls per second at 100
  pending requests.

## R7. Background worker and concurrency

**Decision**: A single worker thread runs inside the backend process. FastAPI's lifespan starts it
when `WORKER_ENABLED` is true, and stops it on shutdown.

- **Steps**: each cycle runs these steps, every 2 seconds and in this order:
  1. **Sync** EUDIPLO sessions (R6) and apply R5 to `pending` requests.
  2. **Expire**: for each `pending` request whose `expires_at` has passed, the worker reads the
     session one last time, then applies R5. A session that is still `active` or `fetched` becomes
     `expired`. There is no extra wait, so an answer that EUDIPLO is still verifying at the
     deadline is lost (spec Clarifications, Session 2026-10-08).
  3. **Cancel**: every open request of a deactivated or deleted form connection becomes
     `unavailable` (R9). Deactivating and deleting already do this themselves, so the step only
     catches a request that a trigger inserted after the deactivation was committed.
  4. *Removed on 2026-10-19*: sending webhook updates (R10). The other steps keep their numbers.
  5. **Delete** EUDIPLO sessions that are due for deletion (R8).
  6. **Re-sync** configurations (R2). This step runs until it has succeeded once after each start.
  7. **Delete** the EUDIPLO configurations of revisions that are no longer current, once no request
     on them still has an EUDIPLO session.
  8. **Delete** expired sign-in sessions.
  9. **Delete** request records `REQUEST_RECORD_RETENTION_SECONDS` (7 days) after the request
     ended (FR-021, R8).
- **Status changes**: every status change, whether from sync, expiry, cancel or pull, locks the request row with `SELECT … FOR UPDATE`. It then checks the current
  status again before changing it. Of two competing changes, only the first one takes effect.
- **Outbound calls**: calls to EUDIPLO, other than the sync list call, run in a small bounded
  thread pool, and the loop never waits for them.
  - **EUDIPLO deletions**: idempotent, because a `404` counts as success.
  - The effect: a slow EUDIPLO call can't delay the sync for other requests (SC-004, SC-007).
- **Errors**: an exception in one step is logged without personal data, and the loop continues.

**Rationale**: The production `Dockerfile` runs a single uvicorn process, so one in-process thread
needs no new service, image or broker. It satisfies Constitution II, because the worker uses the
same sync `Session`. Row locks keep it correct if more processes are ever added. Tests
switch the thread off and call each step directly.

**Alternatives considered**:
- A separate `worker` compose service: a cleaner separation, but more infrastructure for a
  prototype. The step functions can move there later unchanged.
- APScheduler: a dependency that adds nothing over a simple loop.
- Celery or RQ: these need Redis, which is a change to the stack.

## R8. Personal data: no documents stored by the middleware, records kept 7 days (FR-020, FR-021, SC-006) **(user: 7 days)**

**Decision**: The middleware never writes a citizen's documents to its own database, logs or
files.

- **Where the documents stay**: shared documents remain in the EUDIPLO session.
- **When they are held**: the middleware holds them in memory only while delivering them in a
  pull response. At that point it reduces them to exactly the configured fields
  (R9).
- **Status reads**: a status read that has to fall back to `GET /api/session/{id}` (R6) also
  receives `credentials`, and drops them right away.
- **When the EUDIPLO session is deleted**: the worker deletes it with `DELETE /api/session/{id}`:
  - when the repeat window of `PULL_REPEAT_WINDOW_SECONDS` (60 s) after the first delivery ends
    (FR-018, R9);
  - in the cycle after the request becomes `declined`, `verification_failed`, `expired` or
    `unavailable`;
  - for completed requests that were never delivered, at `completed_at` +
    `DOCUMENT_RETENTION_SECONDS` − 60 seconds. The 60-second margin keeps the deletion inside the
    30 minutes despite the 2-second cycle.

  The 30-minute limit also caps the pull repeat window: a window that would run past it ends at
  the limit. Each request records the time its EUDIPLO session was deleted, and a failed delete is
  retried.
- **Where `completed_at` comes from**: EUDIPLO's `consumedAt`, the time the citizen's answer was
  accepted. If the worker was not running, deletion happens as soon as it runs again. The delay an
  outage causes is accepted (user; spec edge case "Outages").
- **Request records (user, FR-021)**: a request **ends** when it has a final status and its
  documents have been delivered or deleted. The row is deleted `REQUEST_RECORD_RETENTION_SECONDS`
  (7 days) after that. A pull with its reference then answers `404`, like an unknown one.
- **Logs**: never claims, tokens or secrets. Request references are removed even from access
  logs (R13). A request is identified by its internal id.

**Rationale**: This follows the EUDIPLO.md rule "Store only the session ID and reference until
results are needed". It also makes SC-006 hold for the middleware's own storage by construction.
SC-006 also covers "the service the middleware uses to communicate with wallets", which is
EUDIPLO. EUDIPLO would keep sessions for 24 hours by default (`SESSION_TTL`), and its cleanup job
runs only every hour. That is why the middleware deletes sessions explicitly instead of relying on
EUDIPLO's retention.

The 7-day retention of request records is the user's choice. It leaves time to look into a failed
request even across a weekend, while records that are pseudonymous personal data don't live
longer than needed.

**Alternatives considered**:
- Copying documents into Postgres, encrypted, until delivery: this needs a key, a new dependency
  and a second copy of the data, for no gain.

## R9. Pull mode: delivering documents once, with a 60-second repeat window (FR-013, FR-018) **(user: repeat window)**

**Open requests**: a request is **open** while it is `pending`, or while it is `completed` and its
documents are neither delivered nor deleted (`documents_delivered_at` and
`eudiplo_session_deleted_at` both empty). Every artifact uses this one definition.

**Decision**: A pull for a `completed` request runs these steps:

1. The request row is locked with `SELECT … FOR UPDATE`.
2. If the documents can no longer be handed out, the answer is `completed` with
   `documents: null`. That is the case once the repeat window after the first delivery has ended,
   or once the EUDIPLO session has been deleted.
3. Otherwise the middleware reads the EUDIPLO session and extracts the configured fields.
4. On the first delivery it sets `documents_delivered_at` and commits.
5. It returns the documents. Deleting the EUDIPLO session is left to the worker (R8), so no slow
   call sits between the commit and the response.

**As implemented (T050)**: no transaction may stay open while EUDIPLO answers (R15), so the
pull checks step 2 without the lock and reads the session in step 3 first. Then it takes the row
lock and checks step 2 again before step 4. If the window ended, or the worker deleted the
session, while EUDIPLO answered, the pull answers `documents: null` and drops what it read. The
first delivery is still the one commit that sets `documents_delivered_at`. The documents also
count as gone from their deletion time on (R8), even before the worker has deleted the session.

**Repeat window (user, FR-018)**: for `PULL_REPEAT_WINDOW_SECONDS` (60 s) after
`documents_delivered_at`, further pulls return the same documents. They are read from EUDIPLO
again and extracted the same way. A serviceBW whose first answer got lost therefore just pulls
again. Two pulls at the same moment both receive the documents, which the window allows.

**Other cases**:
- **EUDIPLO can't be reached in step 2**: nothing changes, and serviceBW receives `502` and can
  retry.
- **EUDIPLO answers `404` for the session**, because the documents are already gone: the request
  records `eudiplo_session_deleted_at`, and the answer is `completed` with `documents: null`.
- **Pulls after the repeat window** return `completed` with `documents: null`.
- **A request that passed its expiry time** while still `pending`: the pull itself makes the last
  check (R7, step 2) before answering.
- **Deactivating or deleting a form connection**: the same transaction turns its open requests
  into `unavailable`, so reactivating it right afterwards can't revive them (FR-006). Its URLs
  answer `409 unavailable` from the next call on (R12), and the deletion step removes the EUDIPLO
  sessions in its next cycle. A trigger that passed the form-connection check before the
  deactivation was committed still inserts its request afterwards, because it doesn't check the
  form connection again after calling EUDIPLO. The worker's cancel step (R7, step 3) turns that
  request into `unavailable` too.
- **Pull and deactivation at the same moment**: a pull that passed the form-connection check before
  the deactivation was committed still finishes. Its documents count as delivered before the
  deactivation took effect.

**Extracting the fields**: The middleware takes the credential entry whose `id` equals the
document type key, and its first `values` object. Each selected field is copied under the field's
key and label; nothing else is copied.

- **SD-JWT VC**: the value is found by walking the claim path, such as `address` → `locality`.
  Technical claims (`iss`, `vct`, `iat`, `exp`) never pass through.
- **mdoc**: EUDIPLO merges the claims of all namespaces into one flat object (verified in
  `mdocverifier.service.ts`), so the value is found by element name.
- **Value types**: binary values are converted to base64 strings and dates to ISO 8601 strings.
  **Verify at implementation** what EUDIPLO's `getPrettyClaims` returns for mdoc binary and date
  values, using a real presentation.
  Nested maps, such as the entries of `driving_privileges`, are emptied to `{}` by EUDIPLO
  ≤ 9.1.0 (R19 item 4).
- **A missing value** can't happen when verification succeeds, because EUDIPLO rejects responses
  with missing claims. If it happens anyway, it is logged by field key and returned as `null`.

**Rationale**:
- **Row lock**: it makes the first delivery a single, well-defined moment, even when two pulls
  arrive together.
- **Allow-list extraction**: it enforces "exactly the configured fields" (SC-005), whatever the
  wallet or EUDIPLO adds.
- **Repeat window**: the user chose it so that a lost answer doesn't lose the documents, and it
  needs no extra call from serviceBW.

**Alternatives considered**:
- Deleting the EUDIPLO session inside the pull before responding: a slow delete could make
  serviceBW time out after the commit, and the documents would be lost.
- Marking a request delivered only after the HTTP response has been sent: the server cannot observe
  that.
- No repeat at all, so a lost answer loses the documents: declined by the user.
- An explicit receipt confirmation from serviceBW: declined by the user. It would add a third call,
  and it isn't confirmed that serviceBW can make it (R20).

## R11. Wallet link and QR code (FR-008)

**Decision**: The trigger response returns three things:

- `wallet_link`: EUDIPLO's `uri`, for opening on the phone that holds the wallet;
- `qr_code_link`: EUDIPLO's `crossDeviceUri`;
- `qr_code`: the `qr_code_link` rendered as a PNG data URI (`data:image/png;base64,…`).

The backend generates the QR code with `segno`. Neither link has a `redirectUri`.

**Rationale**:
- **Two different links**: EUDIPLO returns two `openid4vp://` links. `uri` is the same-device
  variant, and `crossDeviceUri` is "QR code for a wallet on another device … never redirects".
  Showing `uri` as the QR code would be wrong, so the QR code encodes `crossDeviceUri`. It is the
  same request, which is exactly what FR-008 asks for: a link for the device that holds the
  wallet, and a QR code that opens the same request from another device.
- **Why a data URI**: it can be embedded anywhere (`<img src>`, a PDF) without a second call to the
  middleware. serviceBW can still render its own QR code from `qr_code_link`.
- **Why `segno`**: it is pure Python with no dependencies and writes PNG without Pillow.
- **No redirect**: the spec defines no address to return to, so none is used.
  - On the same device, the citizen therefore switches back to the serviceBW form by hand after
    approving. This doesn't change the time to approval that SC-003 measures, but the usability
    test (quickstart V8) should watch for it.
  - Without a redirect, the same-device `response_code` check that EUDIPLO.md describes doesn't
    apply.

**Alternatives considered**:
- An SVG data URI: smaller, but less widely accepted in form and PDF tools.
- A separate QR image endpoint: a second call, and a second network-restricted URL.
- `qrcode` with Pillow: a heavier dependency.

## R12. Connection URLs, request references and "unavailable"

**Decision**:

- **The two URLs**: each is built from `CONNECTION_BASE_URL`, the address at which serviceBW
  reaches the middleware, and the form connection's id, which never changes (FR-005).
  - The trigger URL is `POST {CONNECTION_BASE_URL}/api/connect/{id}/requests`.
  - The pull URL is `GET {CONNECTION_BASE_URL}/api/connect/{id}/requests/{reference}`. The UI shows
    the `{reference}` placeholder literally.
- **Why the trigger is a `POST`**: it creates something. A `GET` must be safe to repeat, and link
  checkers or prefetchers could otherwise start wallet requests.
- **Request references**: `secrets.token_urlsafe(32)`, which is 256 random bits and unique. They
  are separate from the internal request id that EUDIPLO stores in plaintext as `reference`.
- **The "unavailable" answer** comes at two levels.
  - **Form connection level**: while a form connection is deactivated or deleted, every call to
    its URLs answers HTTP `409` with `{"error": "unavailable", "message": …}`, whatever the request
    reference and whatever status the request had reached. This is FR-006's rule that the URLs
    answer every call with "unavailable", whatever status a request has reached.
  - **Request level**: a request that was open when its form connection was deactivated keeps the
    status `unavailable`. After a reactivation, a pull for it therefore answers `200` with
    `status: "unavailable"`.
- **Order of the checks** for both URLs:
  1. Unknown form connection: `404`.
  2. Deactivated or deleted form connection: `409`.
  3. Unknown reference, or a reference that belongs to another form connection: `404`.
- **Deleted form connections**: they become tombstones (`deleted_at`), so their URLs keep answering
  "unavailable" permanently.

**Rationale**:
- **A separate base URL**: the address serviceBW uses may differ from the one the DO.IT UI uses in
  the restricted network, so it is set separately and not derived from the incoming request.
- **Status codes**: a non-2xx code makes the failed trigger explicit to any HTTP client. The
  `error` value carries the spec's status word. The JSON envelope follows Constitution I.

**Alternatives considered**:
- `503` or `410`: `503` suggests a temporary server fault, and `410` fits only deletion.
- A `200` carrying `status: "unavailable"` for the trigger: a naive client would read it as
  success.

## R13. Restricting access to serviceBW (FR-017) **(user: network restriction, enforced by an allow-list in our nginx)**

**Decision**: The connection URLs carry no credentials, and the backend does not authenticate
them. All of them sit under `/api/connect/`, and the production nginx (`frontend/nginx.conf`)
forwards that path **only to clients whose address is on an allow-list**.

- **Setting the allow-list**: `SERVICEBW_ALLOWED_CIDRS` is a comma-separated list of address
  ranges, set on the frontend container.
  - At container start, a script in the nginx image's `/docker-entrypoint.d/` turns it into
    `allow …;` lines followed by `deny all;`.
  - While the variable is empty, the result is `deny all;` alone: the path is **closed by
    default**.
- **The real client address**: `TRUSTED_PROXY_CIDRS` lists the address ranges of the proxy in
  front of nginx, which on Coolify is Traefik. nginx takes the client address from
  `X-Forwarded-For` only when the request comes from those ranges (`set_real_ip_from`,
  `real_ip_header X-Forwarded-For`, `real_ip_recursive on`). The allow-list therefore checks
  serviceBW's address, not the proxy's.
- **Answer to everyone else**: nginx answers `403` and the backend never sees the request.
- **Where the restriction applies**:
  - every deployment that uses the production image, including PR previews, which are therefore
    closed unless configured;
  - **not** local development: there Vite serves the UI and the backend's port 3000 is reachable
    directly on the developer's machine.
- **References kept out of logs**:
  - nginx's access log format uses `$request_uri` with the reference segment of
    `/api/connect/…/requests/<reference>` replaced by `<reference>` (a `map` with a regex).
  - The backend installs a `logging.Filter` on uvicorn's access logger that does the same.
- **Verify at deployment**: a request from an address outside the allow-list gets `403`, and one
  from serviceBW's network gets through. This confirms that Coolify's Traefik replaces any
  `X-Forwarded-For` sent by a client.

**Rationale**:
- **The user's choice**: the user chose network restriction "enforced by the proxy", and an
  allow-list in the repository's nginx.
- **Why closing by default matters**: in the documented Coolify topology, this nginx is the only
  public entry point and forwards all of `/api/`. Without the allow-list, anyone on the internet
  could start genuine City of Stuttgart wallet requests and use them for phishing.
- **Why redact references**: a reference is the key to a request's documents, so it must not
  appear in any log.

**Alternatives considered**:
- A separate internal entry point, or enforcement outside the repository: declined by the user.
- Per-connection API keys, secret URLs or a shared key: declined by the user.

## R14. DO.IT sign-in (FR-007) **(user: personal accounts)**

**Decision**:

- **Accounts**: each account is a row in a `user_accounts` table, with a unique username and an
  Argon2id password hash made with `argon2-cffi`.
  - **Usernames** are stored in lowercase and are 3–100 characters from `a–z 0–9 . _ -`.
  - **Managing accounts** is possible only through the command-line tool `app.cli`, and the UI has
    no account management:
    - `uv run python -m app.cli create-user <username>` prompts for the password twice and requires
      at least 12 characters;
    - `set-password <username>` changes a password and ends the account's sign-in sessions;
    - `delete-user <username>` removes the account together with its sign-in sessions.
  - **Who manages accounts (user)**: the operators of the deployment, on DO.IT's request. DO.IT
    reports joiners and leavers, and a leaver's account is deleted as soon as DO.IT reports the
    departure (spec assumption "Team member accounts").
- **Sign-in sessions**:
  - `POST /api/auth/login` creates a server-side session row in `login_sessions`. The row stores
    the SHA-256 hash of a random token, and the token goes to the browser in the `session` cookie.
  - The cookie is `HttpOnly` and `SameSite=Strict`, with `Path=/api`. It is `Secure` everywhere
    except `APP_ENV=development`.
  - A session lasts `LOGIN_SESSION_HOURS`, 8 hours by default. `POST /api/auth/logout` deletes the
    row.
- **Protected routes**: every management endpoint depends on `get_current_user`. The
  `/api/connect/` and `/api/health` endpoints do not.
- **CSRF**: every management `POST`, `PUT` and `DELETE` requires `Content-Type: application/json`,
  and anything else is answered with `415`. The frontend sends `{}` when an action has no body.
  - `SameSite` alone isn't enough, because it works per site, not per origin. The PR previews
    (`*.my-team.dpschool.app`) and other apps under the same domain count as the same site.
  - A cross-origin page can't send JSON with cookies without a CORS preflight, and that preflight
    passes only for `CORS_ORIGIN` (development) or the app's own origin (production).
- **HTTPS outside development**: the UI must be served over HTTPS everywhere except development.
  The `Secure` cookie and the browser's clipboard API both require it. Coolify's Traefik provides
  TLS.
- **Local development**: open the UI at `http://localhost:5173`, not `127.0.0.1`. `CORS_ORIGIN`
  and the cookie both depend on that host name.

**Rationale**:
- **Server-side sessions**: they need no new library and can be revoked by deleting a row.
- **Argon2id**: it is the current OWASP recommendation, and `argon2-cffi` is its reference binding.
  The 12-character minimum is a baseline in line with NIST SP 800-63B.
- **In local development**: the Vite port and the backend port are on the same site (`localhost`).
  The existing CORS configuration (`allow_credentials=True`, one origin) already allows
  credentialed `fetch`.

**Alternatives considered**:
- JWTs in `localStorage`: exposed to XSS, and can't be revoked.
- `pwdlib` or `passlib`: these are wrappers. `passlib` is unmaintained.
- A shared login, SSO, or protection only by the proxy: declined by the user.
- An `is_active` flag on accounts: there was no command to set it, so accounts are deleted
  instead.

## R15. HTTP client and calls to EUDIPLO

**Decision**: Use `httpx2` (`import httpx2`), already locked at 2.12.0, moved from the `dev` group
to the runtime dependencies.

- **Clients**: one synchronous `httpx2.Client` for EUDIPLO, with timeouts (connect 5 s, read 10 s).
- **Token**: the EUDIPLO access token is cached in memory and renewed 5 minutes before
  `expires_in` runs out. On a `401` it is fetched once more and the call is retried. A lock makes
  this thread-safe.
- **Types**: hand-written Pydantic models describe only the fields the middleware uses. They ignore
  extra fields in responses and send exact bodies in requests. They are written and checked against
  the hosted instance's `$EUDIPLO_URL/api/docs-json`.
- **Database connections**: a handler never holds a connection while waiting for EUDIPLO. It ends
  its read transaction before the call and opens a new one after it. The engine's pool is raised to
  `pool_size=10, max_overflow=20` in `db.py`, and quickstart V7 validates this under load.

**Rationale**: `httpx2` is the maintained continuation of HTTPX, which Pydantic now looks after.
Starlette 1.x's `TestClient` already requires it, so the project gains no new package, and its
`MockTransport` gives the fake EUDIPLO for tests. Sync calls fit Constitution II.

`docs/EUDIPLO.md` §13 says to generate types from the OpenAPI. A generator would add a dev
dependency and code for about 60 endpoints, of which seven are used. Hand-written models for those
seven, checked against the same OpenAPI, follow the intent of that rule.

**Alternatives considered**:
- `requests`: one more package, and it has no transport to mock.
- The original `httpx`: Starlette 1.x no longer uses it.
- Generating a full client with `datamodel-code-generator`: rejected for the reason above.

  - Before release, a review checks every screen:
    - an automated scan in the browser, with axe DevTools or Lighthouse (reviewers' tools, not

    - a walk through the main flows using only the keyboard;
    - a pass with a screen reader (NVDA or VoiceOver);
    - 200% zoom and reflow at a width of 320 px.

**Rationale**:
- **A router**: the SPA needs deep links to a form connection, and `nginx.conf` already falls back

- **No per-account flag**: the user chose "no form connection exists" over "the account's first
  sign-in", so there is no migration, and a new teammate of a team with form connections lands on

**Alternatives considered**:
- View switching held in state: no deep links, and the browser's back button breaks.
- TanStack Router: there is no need for type-safe search params.
- No formal accessibility target, or accessibility out of scope: declined by the user.
- An automated accessibility test suite in the frontend: it would need a test runner, which the
  frontend doesn't have (R17). The review before release covers SC-009.
- Deciding the landing on the overview (`/` with a flag in the router state that redirects from
  there): the overview would show its title before redirecting, and `/get-started` would still
  need its own check.
- A "first sign-in" flag per account: declined by the user (spec Clarifications, 2026-10-11).
- S4's inline form as the first screen: Figma's flow sends sign-in to 02, and S4 is "Your
  connections" with drafts, which the API doesn't have (design-notes.md §5).

## R17. Tests

**Decision**:

- **Tools**: backend tests use `pytest`, added to the `dev` group, with FastAPI's `TestClient`.
- **Database**: a dedicated test database on the compose PostgreSQL. A guard requires the
  database name to end in `_test` before the schema is reset.
- **EUDIPLO**: a fake EUDIPLO built on `httpx2.MockTransport`. It can answer with completed,
  failed (wallet error or verification error) and expired sessions, and with `404` and `409`.
- **Worker**: switched off with `WORKER_ENABLED=false`; its steps are called directly.
- **Coverage**:
  - unit tests for the DCQL builder and configuration hash, field extraction (filtering to the
    allow-list), status mapping (including the last check before expiry) and catalog integrity;
  - API tests for sign-in and CSRF (`415`), form connection CRUD and validation messages, trigger,
    pull (first delivery, 60-second repeat window, expiry, unavailable, check order, EUDIPLO
    `404`), the cancel sweep, re-sync, and deleting
    request records after the retention period.
- **Frontend**: `npm run lint` and `npm run build`, which are the constitution's gates. There is no
  test runner. Accessibility (SC-009) is checked by the review before release (R16, quickstart
  V9).
- **End to end**: a manual run with Paradym against the hosted EUDIPLO, following
  [quickstart.md](quickstart.md). It covers verification failures that only a real issuer can
  produce: untrusted, expired, and revoked credentials.

**Rationale**: `pyproject.toml` already configures pytest (`testpaths = ["tests"]`), but pytest is
not installed. The security-relevant rules here deserve automated checks: exactly the configured
fields, delivered once, data deleted.

The constitution has no test gate yet (TODO(TEST_STRATEGY)). This plan does **not** amend it: the
tests are a non-gating practice, and the decision about a test strategy stays separate. The line
`asyncio_mode = "auto"` refers to a plugin that isn't installed and nothing async is tested, so it
is removed to avoid pytest's unknown-option warning.

**Alternatives considered**:
- SQLite for tests: no `FOR UPDATE SKIP LOCKED`, and no `JSONB` behavior.
- `respx`: an extra package where `MockTransport` is enough.
- Adding Vitest: not requested, and a change to the frontend toolchain.

|---|---|---|
| `SERVICEBW_ALLOWED_CIDRS` | Comma-separated address ranges allowed to reach `/api/connect/` | empty (closed) |
| `TRUSTED_PROXY_CIDRS` | Comma-separated address ranges of the proxy in front of nginx whose `X-Forwarded-For` is trusted | empty (the connecting address counts) |

**Where the values are set**: both compose files pass these variables through. In development,
secrets are read from `backend/.env`, which is not committed (`env_file` with `required: false`).
In production they are set in the Coolify environment.

**Rationale**: The startup check on `CONNECTION_BASE_URL` stops production from showing
`localhost` URLs that DO.IT would copy into serviceBW. It also keeps the pull response, which
carries documents, on HTTPS (FR-019), unless the operators deliberately allow plain HTTP. The flag
also covered webhook addresses until webhook mode was removed on 2026-10-19.

## R19. Points that don't block the plan but need attention later

1. **Registration certificate**. No configuration sets `registration_cert`.
   - EUDIPLO attaches one only if the tenant also has a registrar configuration.
   - If the city later attaches its registration certificate (the WRPRC from the EU sandbox,
     EUDIPLO.md §11), EUDIPLO's overasking check requires every credential query to match an entry
     in the certificate exactly. DO.IT could then request only field sets that the certificate
     registers.
2. **`intent_to_retain`** (mdoc only) is not set. serviceBW keeps the documents in the
   application, so the city may want to declare retention. **Owner: DO.IT, which decides with data
   protection before real citizens use the service (user).**
3. **Differences in the German PID**: `urn:eudi:pid:de:1` has no `date_of_expiry`, and it uses the
   German extension `birth_name`. A field the citizen's PID lacks makes the wallet decline
   (all-or-nothing).
   - This also affects SC-003's first-attempt success. DO.IT should know which fields the targeted
     PIDs contain, and a later iteration could mark such fields in the UI. Not in this iteration
     (user); the spec records it as a known limitation.
4. **Verify at implementation**, against the OpenAPI of the hosted instance
   (`$EUDIPLO_URL/api/docs-json`, `.info.version` 9.x):
   - what `DELETE /api/session/{id}` does: whether it removes `credentials` at once, whether a
     wallet can no longer answer a deleted session, and whether session logs are deleted too
     (`LOG_SESSION_STORE` on the hosted instance must not keep claims);
   - what `POST /api/verifier/config` does with an id that already exists;
   - the list response of `GET /api/session`: paging, and whether items carry `failureCode` and
     `consumedAt`;
   - the exact id and description limits for presentation configurations;
   - the representation of mdoc binary and date values;
   - that an expired credential fails verification.

   **Checked on 2026-10-09 (T018)** against `https://eudiplo.faro.dpschool.app/api/docs-json`, which
   reports `.info.version` 9.0.0. The request bodies of all seven calls match
   [contracts/eudiplo-usage.md](contracts/eudiplo-usage.md), and both example bodies there validate
   against the OpenAPI schemas. Only the OpenAPI was checked, because no API client credentials
   were used.

   | Point | Answer |
   |---|---|
   | `DELETE /api/session/{id}` | **Not settled**. The OpenAPI only says "Deletes a session by its ID" (`204`). Whether `credentials` go at once, whether a wallet can still answer, and what happens to the session log are checked live in T081 |
   | `POST /api/verifier/config` with an existing id | **Settled**: "If it already exists, it will be updated." It answers `201`, never `409`. Whether an update replaces or merges isn't stated; the middleware always sends a complete body, so either works |
   | List response of `GET /api/session` | **Settled**. It pages: `page` (from 1) and `pageSize` (default 25, at most 100), answered as `{items, total, page, pageSize, totalPages}`. Each item has the full `Session` schema, with `failureCode` and `consumedAt` when they are set, so the sync needs no `GET /api/session/{id}` per item |
   | Id and description limits | **Partly settled**. The configuration `id` needs at least one character and has no maximum, and `description` has no limit. A DCQL credential query `id` must match `^[A-Za-z0-9_-]+$`, which the catalog keys `pid` and `mdl` do |
   | mdoc binary and date values | **Partly settled** (bug `mdl-driving-privileges-empty`, from EUDIPLO v9.0.0's source and `@owf/cose@0.4.0`): a top-level `full-date` arrives as `"YYYY-MM-DD"`, a `bstr` as `{"0": …}` (turned into base64), but nested CBOR maps arrive as `{}`: `getPrettyClaims` leaves them JS `Map`s and the session column is written with `JSON.stringify`. `driving_privileges` is therefore `[{}, …]` in EUDIPLO ≤ 9.1.0; the middleware logs a warning by field key. Live shapes still checked in T081 |
   | An expired credential fails verification | **Not settled**: the failure codes aren't enumerated. Quickstart V3 |

   **Differences from the contract**, and how the code handles them:
   - **Error answers aren't documented**. Of the codes the contract relies on, the OpenAPI lists
     only the token's `401`. The `404` of `GET` and `DELETE /api/session/{id}` and the `409` of
     `POST /api/verifier/offer` come from `docs/EUDIPLO.md`. The client maps them as the contract
     says, and T081 confirms them live.
   - **`crossDeviceUri` is optional** in the offer response, while the contract turns it into
     `qr_code_link` and `qr_code` unconditionally. The client reads it as optional. **Decided
     (user, 2026-10-11)**: an offer without it answers `502`, like any other failed offer. The
     trigger (T049) deletes the new EUDIPLO session again, stores nothing, and logs the
     request's internal id. It doesn't fall back to `uri`, the same-device link (R11).
   - **The offer can also answer with a PNG** (`image/png`), so every call sends
     `Accept: application/json`.
   - **List items may contain `credentials`**, because they use the full `Session` schema. The
     client's list model leaves `credentials` out, and no response body is ever logged.
   - **Paging and the cursor** (R6): `updatedFrom` is inclusive and must be UTC with seconds, so the
     client sends it as `…000Z`, sorted by `updatedAt` ascending, 100 items per page. The sync
     (T053) reads every page of a cycle: more than 100 updates inside the 5-second overlap would
     otherwise keep the cursor from moving. Each page after the first starts at the last
     `updatedAt` of the page before, rather than at the next page number. A session that changes
     while the pages are read moves to the end of the list, so with page numbers it would push an
     unread session onto a page already read. Only a page whose items all share one `updatedAt`
     is followed by the next page number.
   - **Strict bodies**: unknown keys, and `null` for optional arrays such as `claim_sets`, are
     rejected. The configuration body (T033) leaves unused keys out instead of sending `null`, and
     `lifeTime` must be an integer of at least 1.
   - **Token response**: `expires_in` is a number, and `state` and `token_type` are marked required.
     The client reads only `access_token` and `expires_in`.

   **Whether Paradym reports a decline (T081, V3)**: it doesn't. Paradym 1.20.2 sends no error
   response, so a declined request stays `pending` until `expired`. This comes from its source
   and one live run on 2026-10-13 (R5). The other T081 points are still open.
5. **Tenant settings**: lowering the session TTL of tenant `dps` as a backstop to R8 is a decision
   for its operators. EUDIPLO's hourly cleanup job means the TTL alone can't guarantee 30 minutes.
6. **One tenant for every environment (accepted for now, R2)**. Before real citizens use the
   service, production should get its own tenant or instance, with its own client and trust list.
   DO.IT owns this (user).
   - Until then:
     - configuration ids contain a UUID, so they never collide;
     - the session sync ignores sessions it doesn't know;
     - configurations left behind by reset development databases must be removed in the EUDIPLO
       console.
7. **Sign-in hardening**: there is no rate limit or lockout for failed sign-ins, and no password
   policy beyond the 12-character minimum. The user accepted both for now. A limit on failed
   sign-ins is to be added before real citizens use the service (spec, "Out of scope").

## R20. What serviceBW is expected to do **(user: not sure yet, to be confirmed by DO.IT)**

The design relies on serviceBW doing the following.
- **Items 1–4 and 7** are expectations the user could not confirm yet. DO.IT confirms them with
  serviceBW before the integration, and the URL design is adjusted if one of them doesn't hold.
  The spec records them in the assumption "serviceBW's capabilities".
- **Item 6** is decided, and is now the spec assumption "serviceBW waits for a final status".

1. **Trigger**: call the trigger URL with an HTTP `POST` that has no body, from its server and not
   from the citizen's browser.
2. **Pull URL**: put the request reference into the pull URL (`GET …/requests/{reference}`). If an
   answer gets lost, pull again within 60 seconds to receive the same documents (FR-018).
3. **Responses**: read JSON responses in the `{"data": …}` / `{"error": …, "message": …}`
   envelopes, and act on `404` and `409`.
4. **QR code**: show a PNG given as a data URI, or render its own QR code from `qr_code_link`.
5. *Removed on 2026-10-19*: accepting webhook updates (webhook mode is out of scope).
6. **Waiting until a final status (decided by the user; spec assumption)**. serviceBW keeps
   pulling, every 2 seconds, until the status is no longer `pending`. It reacts at once to `declined`, `verification_failed` and
   `expired`.
   - It does **not** apply a timeout of its own that is shorter than `expires_at`, which is
     10 minutes.
   - The mock middleware this replaces answered "not found" while waiting and after a failure, and
     the test form gave up after 3 minutes. Against this middleware, a 3-minute timeout would
     abandon citizens who approve between minutes 3 and 10. Their documents would never be
     collected, and they would be deleted after 30 minutes.
7. **Checking the applicant**: serviceBW checks that the documents it receives belong to the
   applicant, for example against the signed-in serviceBW account (spec assumption "Documents
   match the applicant"). The middleware can't do this, because it never learns who filled in the
   form. Until serviceBW confirms it, the risk of a link or QR code forwarded to someone else is
   accepted for this iteration (user).

## R21. Smaller decisions

| Decision | Reason |
|---|---|
| The serviceBW form is a free-text field of 1–500 characters, and several form connections may name the same form | There is no integration with serviceBW's admin side (spec, Key Entities) |
| When two team members edit the same form connection at once, the later save wins (user) | There is no version check; that is fine for a small team (spec edge case "Two team members editing at once") |
| Form connection names don't have to be unique | No requirement asks for it, and the id identifies a form connection |
| Each document type appears at most once per form connection | DCQL credential query ids must be unique, and a second copy of the same document adds nothing |
| The overview lists the most recently updated form connections first | No order is specified, and this one is consistent with the template |
| A deactivated form connection can still be edited | It lets DO.IT prepare changes before reactivating |
| Validation messages come from the service layer, not from Pydantic | The template's handler for `RequestValidationError` only says "Invalid request payload", and US1 scenario 3 needs messages that name the problem |
