# Data Model: serviceBW ↔ EUDI Wallet Form Connections

**Phase 1 output of `/speckit-plan`** | **Date**: 2026-10-07 | **Spec**: [spec.md](spec.md) |
**Research**: [research.md](research.md)

The tables below follow Constitution V:
- SQLAlchemy 2.0 `Mapped` / `mapped_column`;
- UUID4 primary keys stored as `String(36)`;
- `created_at` and `updated_at` as `DateTime(timezone=True)` with `server_default=func.now()`;
- `snake_case` names, and an index on every column used to look rows up, including the worker's
  scans (see [Indexes](#indexes)).

They are created by one new autogenerated migration, which also drops the template's
`team_members` table (research R1). A second migration (2026-10-19) removes webhook mode again:
it drops the `webhook_deliveries` table, `form_connections.webhook_url`,
`document_requests.webhook_url` and `document_requests.mode` (spec Clarifications, Session
2026-10-19).

**No table holds a citizen's documents.** Shared documents stay in the EUDIPLO session until the
middleware delivers them, and then the worker deletes that session (research R8).

## Spec entities and where they live

| Spec entity | Stored as |
|---|---|
| Form Connection | `form_connections`, plus the documents of its current revision |
| Document Type | The catalog in code (`app/catalog.py`), not in the database |
| Requested Document | One entry in `form_connection_revisions.documents` |
| Connection URL | Not stored. Built from `CONNECTION_BASE_URL` and the form connection's `id` |
| Document Request | `document_requests`. The documents themselves stay in EUDIPLO until delivered. The rows are deleted 7 days after the request ended (FR-021) |
| DO.IT Team Member | `user_accounts`, plus `login_sessions` |

## Relationships

```text
user_accounts 1 ──< login_sessions

form_connections 1 ──< form_connection_revisions 1 ──< document_requests
        1 └───────────────────────────────────────────< document_requests
```

## Open requests

A document request is **open** while it is:
- `pending`, or
- `completed` with documents that are neither delivered nor deleted: both
  `documents_delivered_at` and `eudiplo_session_deleted_at` are empty.

This is what FR-006 calls "in progress": deactivating or deleting a form connection cancels its
open requests. Every artifact uses this one definition.

## Ended requests

A document request **ends** when it has a final status and its documents have been delivered or
deleted (FR-021). `ended_at` records that moment. The worker deletes the row
`REQUEST_RECORD_RETENTION_SECONDS` (7 days) later. A pull with that reference then
answers `404`, like an unknown one.

|---|---|---|

Accounts exist only through the command-line tool `app.cli`, and the management interface has no
account management (FR-007):
- `create-user` adds an account.
- `set-password` changes a password and deletes that account's `login_sessions`.
- `delete-user` removes the account and, through the cascade, its sessions.

## `form_connections`: Form Connection (FR-001, FR-004 to FR-006)

| Column | Type | Rules |
|---|---|---|
| `id` | `String(36)` PK | UUID4. Part of both connection URLs, so it never changes (FR-005) |
| `name` | `String(200)` | Required. 1–200 characters after trimming. Doesn't have to be unique |
| `servicebw_form` | `String(500)` | Required. 1–500 characters after trimming. Free text identifying the serviceBW form, such as its name or id |
| `is_active` | `Boolean`, default `true` | `false` means deactivated (FR-006) |
| `current_revision` | `Integer` | The revision that new requests use |
| `deleted_at` | `DateTime(timezone=True)`, nullable, indexed | Marks the row as deleted; it is kept so its URLs keep answering "unavailable" (FR-006) |
| `created_at`, `updated_at` | `DateTime(timezone=True)` | |

**Values derived in API responses, not stored**:
- `trigger_url`: `{CONNECTION_BASE_URL}/api/connect/{id}/requests`.
- `pull_url`: `{CONNECTION_BASE_URL}/api/connect/{id}/requests/{reference}`.

**What deactivating and deleting change**: deactivating sets `is_active=false`, and deleting sets
`deleted_at`. The same transaction turns every [open request](#open-requests) of the form
connection into `unavailable` (FR-006), so reactivating it right afterwards can't revive them.
From the next call on, the URLs answer `409 unavailable`. Neither calls EUDIPLO: the worker
deletes the EUDIPLO sessions in its next cycle. A trigger that passed the form-connection check
before the deactivation was committed still inserts its request afterwards, and the worker's
cancel step turns that one into `unavailable` too (research R9).

**Validation (FR-003)**: The service layer checks these rules. A failure raises `HTTPException(400)`
with `{"error": "Validation error", "message": …}`, and the message names the problem
(US1, scenario 3).

| Rule | Example message |
|---|---|
| At least one document | "Add at least one document." |
| Document type exists in the catalog | "Unknown document type 'xyz'." |
| Each document type at most once | "'Personal ID' is added more than once." |
| At least one field per document | "Select at least one field for 'Personal ID'." |
| Every field exists for its document type, and none twice | "Unknown field 'abc' for 'Personal ID'." |
| Name and serviceBW form present and within limits | "Enter a name.", "Enter the form ID." (the UI calls the serviceBW form "Form ID") |

The request schemas accept empty lists on purpose. The template's generic handler for
`RequestValidationError` only answers "Invalid request payload", so these checks happen in the
service layer, where the message can name the problem.

## `form_connection_revisions`: the documents and fields requested (FR-003, FR-005, FR-009)

| Column | Type | Rules |
|---|---|---|
| `id` | `String(36)` PK | UUID4 |
| `form_connection_id` | FK → `form_connections.id`, indexed | |
| `revision` | `Integer` | Starts at 1. Unique together with `form_connection_id` |
| `documents` | `JSONB` | Ordered list of Requested Documents (see below). Never changed after insert |
| `lifetime_seconds` | `Integer` | `REQUEST_LIFETIME_SECONDS` when the revision was created. It equals the configuration's `lifeTime`, and the expiry of every request on this revision derives from it |
| `config_hash` | `String(64)` | SHA-256 of the canonical EUDIPLO configuration body, without its `id` and `description`, so that renaming a form connection creates no revision. Used to detect changes to the catalog, trust list or lifetime (research R2) |
| `eudiplo_config_id` | `String(255)`, unique | `fc-{form_connection_id}-r{revision}`: the EUDIPLO presentation configuration for this revision |
| `eudiplo_config_deleted_at` | `DateTime(timezone=True)`, nullable | Set once the EUDIPLO configuration has been deleted |
| `created_at`, `updated_at` | `DateTime(timezone=True)` | |

**Requested Document**: one entry in `documents`. Fields are stored in catalog order.

```json
[
  { "document_type": "pid", "fields": ["family_name", "given_name", "birthdate", "address_locality"] },
  { "document_type": "mdl", "fields": ["expiry_date", "document_number", "driving_privileges"] }
]
```

**When a revision is created**:
- with the form connection, as revision 1;
- when the documents or fields change, as revision n+1;
- by the worker's re-sync after a start, when the configuration generated for the current
  documents with the current settings (the catalog, `EUDIPLO_TRUST_LIST_ID` and
  `REQUEST_LIFETIME_SECONDS`) no longer matches `config_hash` (research R2);
- never because the name or the serviceBW form changed.

**Creating a revision**:
1. Lock the `form_connections` row (`SELECT … FOR UPDATE`).
2. Take the next revision number.
3. Create the EUDIPLO configuration, with the DCQL from research R3 and `lifeTime =
   lifetime_seconds`.
4. Insert the revision, update `current_revision`, and commit.

If EUDIPLO fails in step 3, nothing is saved, and the UI receives a `502` error. If the commit
fails after step 3, the configuration is deleted again (best effort, logged).

**Deleting the EUDIPLO configuration**: the worker deletes it once both of these hold:
- the revision is no longer current, or its form connection was deleted;
- no request on the revision still has an EUDIPLO session (`eudiplo_session_deleted_at` empty).
  This includes requests inside the pull repeat window.

## `document_requests`: Document Request (FR-008 to FR-013, FR-018 to FR-021)

| Column | Type | Rules |
|---|---|---|
| `id` | `String(36)` PK | UUID4. Internal id, sent to EUDIPLO as the session `reference` (contains no personal data) |
| `reference` | `String(64)`, unique, indexed | The request reference returned to serviceBW: `secrets.token_urlsafe(32)` (FR-018). Never logged |
| `form_connection_id` | FK → `form_connections.id`, indexed | |
| `revision_id` | FK → `form_connection_revisions.id`, indexed | The configuration in force when the request was triggered (FR-005) |
| `status` | `String(32)`, indexed | `pending`, `completed`, `declined`, `verification_failed`, `expired` or `unavailable` (FR-011) |
| `failure_code` | `String(100)`, nullable | EUDIPLO's `failureCode`, kept for diagnostics only. Not personal data |
| `eudiplo_session_id` | `String(255)`, unique | The EUDIPLO session behind this request |
| `expires_at` | `DateTime(timezone=True)`, indexed | Trigger time + the revision's `lifetime_seconds` (FR-012) |
| `status_changed_at` | `DateTime(timezone=True)` | When `status` last changed |
| `completed_at` | `DateTime(timezone=True)`, nullable | When the citizen shared: EUDIPLO's `consumedAt`. The 30-minute limit (FR-020) starts here |
| `documents_delivered_at` | `DateTime(timezone=True)`, nullable | Set on the first delivery: the first pull that returns the documents. Pulls within `PULL_REPEAT_WINDOW_SECONDS` (60 s) after it return the same documents. After that the documents can't be obtained again (FR-018) |
| `eudiplo_session_deleted_at` | `DateTime(timezone=True)`, nullable | Set once the EUDIPLO session, with any shared documents, has been deleted, or EUDIPLO reported it gone (FR-020) |
| `ended_at` | `DateTime(timezone=True)`, nullable, indexed | When the request [ended](#ended-requests). For `declined`, `verification_failed`, `expired` and `unavailable` this is the status change; for `completed`, the first delivery, or the deletion of the undelivered documents. The row is deleted `REQUEST_RECORD_RETENTION_SECONDS` (7 days) later (FR-021) |
| `created_at`, `updated_at` | `DateTime(timezone=True)` | |

### Request status transitions

```text
 trigger ─▶ pending ──┬── EUDIPLO completed ──────────────▶ completed
                      ├── wallet error code ──────────────▶ declined
                      ├── verification failure ───────────▶ verification_failed
                      ├── last check after expires_at:
                      │   R5 table applied;
                      │   still active or fetched ────────▶ expired
                      └── form connection deactivated
                          or deleted ─────────────────────▶ unavailable

 completed ──┬── first delivery (first pull that returns ─▶ documents_delivered_at and ended_at set;
             │   the documents)                            EUDIPLO session deleted when the 60 s
             │                                             pull repeat window ends
             ├── completed_at + 30 min − 60 s,
             │   still undelivered ────────────────────────▶ EUDIPLO session deleted, ended_at set
             │                                             (status stays completed, no documents)
             └── form connection deactivated or
                 deleted while open ───────────────────────▶ unavailable

 every ended request ── ended_at + 7 days ─────────────────▶ row deleted
```

- **Mapping**: the mapping from EUDIPLO session states and failure codes is in research R5. The
  last check before expiry applies it too, so a decline just before the deadline stays `declined`.
- **Final statuses**: `declined`, `verification_failed`, `expired` and `unavailable` never change.
  `completed` changes only to `unavailable`, and only while the request is open.
- **Locking**: every status change locks the request row (`SELECT … FOR UPDATE`) and checks the
  current status again first (research R7).
- **Every status change** sets `status_changed_at`.
- **Deleting the EUDIPLO session**: the worker deletes it when the pull repeat window ends, and
  for every final status. Each deletion sets
  `eudiplo_session_deleted_at`.
- **Deleting the record**: `ended_at` is set when the request [ends](#ended-requests). Seven days
  later the worker deletes the row (FR-021).

## Indexes

Besides the primary keys, the unique columns and the foreign keys listed above, the worker's
scans use these indexes:

| Table | Index | Used by |
|---|---|---|
| `document_requests` | `(status, expires_at)` | The expiry scan for `pending` requests |
| `document_requests` | Partial on `(status)`, `WHERE eudiplo_session_deleted_at IS NULL` | The EUDIPLO session deletion scan, the configuration cleanup, and finding open requests. It covers only the few requests whose session still exists |
| `document_requests` | `(ended_at)` | Deleting request records after `REQUEST_RECORD_RETENTION_SECONDS` (FR-021) |
| `form_connection_revisions` | Partial on `(form_connection_id)`, `WHERE eudiplo_config_deleted_at IS NULL` | The configuration cleanup scan |
| `form_connections` | `(deleted_at)` | The overview, and the cancel sweep |
| `login_sessions` | `(expires_at)` | Removing expired sign-ins |

## Document type catalog

The catalog lives in `app/catalog.py`, and `GET /api/document-types` serves it. Each document type
has a `key`, a `label`, a credential format, the format's identifiers, and an ordered list of
fields. Each field has a `key`, a `label` and a claim path.

- **Field keys** are stable: they appear in the API and in the documents delivered to serviceBW.
- **Labels** are UI copy. They use the Figma design's wording where the design names a field
  (decided 2026-10-10, [design-notes.md](design-notes.md) §8), and this list's wording elsewhere.
- **Requests**: every field selected for a request is required (research R3).

### How a delivered document is identified (FR-013)

Each delivered document carries its `document_type` and `label`. Each field carries its `key`,
`label` and `value`. Values keep their JSON type (string, number, boolean, array or object).
Binary values become base64 strings, and dates become ISO 8601 strings (research R9). The full
shape is in [contracts/integration-api.md](contracts/integration-api.md).
